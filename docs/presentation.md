## Slide 2 — The problem: protocols you cannot see
- Purpose: Show why memorising protocols leaves students unable to reason about failures.
- On-slide text:
  - Students memorise protocols but cannot see them run.
  - Timing, layers, routing tables and failures stay invisible.
  - Exam answers describe behaviour nobody has watched happen.
- Visual: Left: a textbook rectangle labelled "Definitions: TTL, ARP, RIP, OSPF". Right: four dashed-outline boxes with a closed-eye icon, labelled "Timing", "Layers", "Tables", "Failures". A grey arrow from the textbook to the four boxes labelled "no view".
- Animation: 1st textbook; 2nd the four boxes one at a time (Timing, Layers, Tables, Failures); 3rd the "no view" arrow. Transition: push from right.
- Speaker notes: In a computer networks course we learn that TTL decrements at every router, that ARP resolves addresses, and that OSPF recovers faster than RIP. But a textbook cannot show how many milliseconds a packet spends in each queue, what a switch does with an unknown destination, or what happens to a TCP connection when a link dies. Without that view, a student can recite definitions yet still cannot predict what a failure will do. That gap is what this project addresses.

## Slide 7 — The simulation engine: virtual clock, seeds, speed
- Purpose: Explain how slow motion and repeatability work.
- On-slide text:
  - Discrete-event queue ordered by a virtual clock.
  - Seeded random numbers: same seed, same run.
  - Speed 0.1× to 10×; pause, step, scrub.
- Visual: A timeline axis labelled "virtual time (ms)" with five event dots (t=0.000 encapsulate, 0.100 ARP who-has, 3.811 transmit, 5.869 router LPM, 8.374 ARP reply — taken from screenshot 07). Above the axis a priority-queue icon labelled "event queue". Right: a speed dial with ticks 0.1×, 0.25×, 1×, 10× and the caption "1× = 10 ms per real second". Bottom-right: small `07-slow-motion-layer-view.png`.
- Animation: 1st axis; 2nd the five dots left to right; 3rd queue icon; 4th speed dial; 5th screenshot. Transition: fade.
- Speaker notes: The engine is a discrete-event simulator. Every packet action becomes an event on a queue ordered by virtual time, so the clock jumps from event to event and the player can run it at any speed. At one-times speed, ten milliseconds of network time pass per real second, so a few-millisecond ping is watchable. Randomness for loss and jitter comes from a seeded generator, so the same seed gives exactly the same run, which makes demos and tests repeatable.
- Source: `frontend/src/sim/des.ts` (event queue; `random()` = mulberry32 at line 82); `frontend/src/features/sim/playback.ts:6` (`SIM_MS_PER_SECOND = 10`); `frontend/src/sim/des.test.ts` ("same seed, same run; loss makes seeds differ" — passed in `npm test`); docs/sim_model.md §5; screenshot 07 event times.

## Slide 8 — The timing model, with a worked example
- Purpose: Show the per-hop formula and verify it by hand against the simulator.
- On-slide text: hop delay = t_proc + t_queue + t_tx + t_prop
- Visual: Top: the formula in four coloured chips: `t_proc` (device table), `t_queue = ρ/(1−ρ) × t_tx` (M/M/1/K), `t_tx = bits ÷ bandwidth`, `t_prop = length ÷ 2×10⁸ m/s`. Middle: path diagram h1 – sw1 – r1 – r2 – sw2 – h2 with link labels (100 Mbps, 1 ms) (1000 Mbps, 0.5 ms) (100 Mbps, 2 ms) (1000 Mbps, 0.5 ms) (100 Mbps, 1 ms). Bottom table "ICMP echo, 98 B": propagation 5 ms; processing 1.3 ms; transmission 0.025088 ms; queueing 0; **one-way 6.325088 ms**; **RTT 12.650176 ms**. Footer: "1500 B at 10 Mbps = 1.2 ms; 2 km = 0.01 ms".
- Animation: 1st the four formula chips one at a time; 2nd the path diagram; 3rd the table rows top to bottom; 4th the bold totals; 5th the footer. Transition: push from right.
- Speaker notes: Each hop costs processing, queueing, transmission and propagation. Transmission is bits divided by bandwidth: 1500 bytes on 10 megabits is 1.2 milliseconds. Propagation is length over two hundred million metres per second. Here is a worked example from our unit test: a 98-byte ping across five links. Propagation is 1 plus 0.5 plus 2 plus 0.5 plus 1, which is 5 milliseconds; processing adds 1.3; transmission adds 0.025. The total, 6.325 milliseconds, matches the simulator exactly, and the round trip is double.
- Source: docs/sim_model.md §1–2; `frontend/src/sim/engine.test.ts` tests "1500-byte packet over a 10 Mbps, 2 km link", "hand-calculated ping h1 -> h2", "M/M/1/K queue estimate"; `frontend/src/sim/testkit.ts` (lab links); `measurements.txt` "PING before"; `frontend/src/sim/des.test.ts` ("unloaded DES timing equals the analytical calculator"). Processing by hand: 0.1+0.05+0.5+0.5+0.05+0.1 = 1.3; transmission by hand: 3×(98×8/100 Mbps = 0.00784 ms) + 2×(98×8/1000 Mbps = 0.000784 ms) = 0.025088 ms.

## Slide 9 — Layers in motion: what each device does
- Purpose: Show encapsulation and the highest layer each device type touches.
- On-slide text:
  - Hosts encapsulate L7 down to L1; routers open up to L3.
  - Switches learn MACs and flood; hubs just repeat bits.
  - Firewalls add allow/deny rules on top of routing.
- Visual: A five-row ladder, one row per device, each with a layer bar of four segments (L1, L2, L3, L7) lit up to its depth: Hub/Repeater L1 (1 lit), Switch/AP L2 (2 lit), Router L3 (3 lit), Firewall L3 + rules (3 lit + shield), Host L7 (4 lit). On the right: crop of `07-slow-motion-layer-view.png` showing "r1 up to L3 Network … longest-prefix match … TTL 64→63".
- Animation: Rows appear top to bottom (hub, switch, router, firewall, host), each bar filling left to right; then the screenshot crop. Transition: fade.
- Speaker notes: This is the layer view. When a ping leaves host h1 it is wrapped at layer 7, then 4, 3 and 2, and sent as bits. The hub or repeater only repeats bits. The switch reads the layer-2 header, learns the source MAC address and either forwards or floods. The router strips the layer-2 header, does a longest-prefix match, decrements TTL and builds a new header. The firewall also applies allow or deny rules. Students can open any packet and see these steps.
- Source: docs/sim_model.md §3 (devices table); `frontend/src/features/sim/player.tsx` (layer view); `frontend/src/sim/engine.ts` `DEVICE_LAYER`; `frontend/src/sim/des.test.ts` (switch floods then learns; hub repeats bits; TTL expiry); screenshot 07.

## Slide 10 — Routing in action: static vs RIP vs OSPF
- Purpose: Show measured convergence differences after the same failure.
- On-slide text: Same cut, three outcomes: never, ~9 s, ~0.2 s (SIMULATED).
- Visual: Left: horizontal bar chart "Time to converge after link l3 goes down (simulated time)" with bars — Static: "never" (hatched bar to the axis end); RIP: 9.47 s (seed 1; range 7.30–10.93 s over seeds 1–5); OSPF: 0.207 s. Right: table "Flow h1→h2": Static outage permanent / lost all; RIP outage 8.41 s / 841 packets @100 pps; OSPF outage 0.200 s / 20 packets. ## Slide 11 — Protocol scenarios and how failures change them
- Purpose: Show that protocol ladders react to faults, using TCP as the example.
- On-slide text:
  - ICMP, ARP, DHCP, DNS, TCP, UDP and HTTP as ladder diagrams.
  - A fault mid-scenario changes the ladder, not just the result.
  - Under static routing TCP gives up; under OSPF it completes.
- Visual: Left: a seven-chip row "ICMP · ARP · DHCP · DNS · TCP · UDP · HTTP". Centre: `14-tcp-ladder-failure.png`. Right: a timeline of the TCP failure with exact data: SYN t=0 → 6.315 ms; SYN-ACK → 12.631 ms; ACK → 18.946 ms; data lost; retransmits at 1.026 s, 3.026 s, 7.026 s; "Connection reset after 3 retransmissions" at 15.026 s.

- Speaker notes: Each protocol is a ladder diagram, and every message's delay is taken from the same engine, so a fault injected mid-scenario has real consequences. ## Viva Q&A

1. **What is simulated?** Everything: delay, queues, routing tables, convergence and packet events are calculated by an educational model in the browser (`frontend/src/sim/`). Nothing is measured on equipment and no real packets are captured.
2. **What is the per-hop delay formula?** `t_proc + t_queue + t_tx + t_prop`. Transmission is bits ÷ bandwidth, propagation is length ÷ 2×10⁸ m/s (or the configured delay), processing depends on device type, queueing comes from the M/M/1/K estimate.
3. **Give a worked number.** 1500 B on 10 Mbps = 1.2 ms transmission; 2 km = 0.01 ms propagation. The 98 B ping across five links costs 6.325 ms one-way, 12.650 ms RTT (unit test).
4. **How is queueing modelled?** Calculator: M/M/1/K with wait `ρ/(1−ρ)×t_tx` and tail-drop probability `(1−ρ)ρ^K/(1−ρ^(K+1))`. Packet simulator: an explicit FIFO per link direction with tail drop when K packets wait.
5. **Why does RIP converge slower than OSPF?** RIP learns by periodic (30 s) and triggered (1–5 s random delay) distance-vector updates passed neighbour to neighbour, and a break behind a switch waits for the 180 s invalid timer. OSPF floods a link-state advertisement immediately and runs SPF 200 ms later. Measured here: RIP 7.3–10.9 s, OSPF 207 ms.
6. **What does static routing do after a failure?** Nothing: routes are computed once from the design, so traffic is blackholed until the student restores the link or edits routes.
7. **What is TTL for?** It stops packets looping forever: every router decrements it, and at 0 the router drops the packet and sends ICMP Time Exceeded. Traceroute uses TTL 1, 2, 3… to reveal each router.
8. **What does ARP do here?** It maps an IP to a MAC on the local segment. The first frame from each L3 hop is preceded by a who-has broadcast and is-at reply, which also teaches switches the MACs. A "warm ARP" option skips it.
9. **How does a switch differ from a hub?** A switch learns source MACs per port and forwards on a table hit, flooding unknown unicast; a hub repeats bits out of every port at layer 1 (collisions are not simulated).
10. **How is determinism achieved?** A seeded mulberry32 PRNG drives loss, jitter and RIP timer phases, so the same seed gives the identical event list (tests compare runs with `deepEqual`).
11. **How is AI output validated?** Model text must be strict JSON; the server checks device counts (≤ 50), unique names/IPs and connectivity; explanations may only contain numbers found in the simulator's facts; suggestions are checked against real devices/links and need a preview and a click.
12. **What if the AI is wrong or down?** The answer is rejected or the call fails, and a labelled local rule-based planner answers ("not AI"). A circuit breaker opens after 3 failures; the UI always states who answered.
13. **Can a prompt inject commands?** The student's text is quoted as untrusted data in the prompt, the model can only return JSON values, and nothing from the model is executed (`test_prompt_injection_is_quoted_as_data_and_output_still_validated`).
14. **How do you find single points of failure?** Tarjan's low-link algorithm gives articulation points and bridges on the graph of up devices and links; "if X fails, N devices lose reachability" is the devices that leave the largest connected group; Brandes' algorithm gives betweenness.
15. **What are the main limits?** Simulated and simplified (no STP, VLAN, NAT, IPv6, collisions, full TCP, vendor CLI); login is an emulator and the network API has no per-user ownership; no study of learning outcomes.
